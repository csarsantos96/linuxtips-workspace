### Resposta do aluno

A principal motivação seria reduzir a superfície de ataque da imagem.
Uma imagem distroless contém apenas o runtime necessário, como o Node.js, e os arquivos da aplicação, sem shell, gerenciadores de pacotes ou utilitários extras. Isso resulta em:
- imagem menor;
- menos vulnerabilidades potenciais;
- menor consumo de recursos;
- maior dificuldade para executar comandos maliciosos dentro do container.
Para produção, eu escolheria distroless quando não precisasse acessar o container para executar comandos de diagnóstico.

Agora, vamos aprofundar um pouco. Você está construindo uma imagem `distroless` para uma aplicação Java. Você sabe que a imagem final precisa conter o JAR da sua aplicação e o Java Runtime Environment (JRE). Como você faria para garantir que apenas o JRE e o JAR da sua aplicação sejam incluídos na imagem `distroless`, sem nenhum outro binário ou biblioteca do sistema operacional?

### Resposta do aluno

Eu faria um build em múltiplos estágios (multi-stage build). No primeiro estágio, compilaria a aplicação; no estágio final, usaria uma imagem distroless Java e copiaria apenas o JAR:
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app

COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

FROM gcr.io/distroless/java21-debian12:nonroot
WORKDIR /app

COPY --from=build /app/target/minha-aplicacao.jar app.jar

ENTRYPOINT ["java", "-jar", "app.jar"]

A imagem final contém o JRE da imagem Distroless e somente o JAR copiado do estágio de compilação, sem Maven, código-fonte, shell ou ferramentas adicionais.
