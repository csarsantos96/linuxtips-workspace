Diferença entre git push e git pull

    git push (Envio): Envia os commits realizados localmente para o repositório remoto, atualizando as branches remotas com o seu histórico local.

    git pull (Recebimento / Atualização): Baixa as alterações e commits do repositório remoto e os mescla automaticamente na sua branch local atual (atuando internamente como uma combinação de git fetch + git merge ou git rebase).

Depois de fazer alguns commits nessa branch, você percebe que precisa urgentemente corrigir um bug crítico que está na branch principal (`main`). Como você faria para alternar rapidamente para a branch `main`, fazer a correção, e depois voltar para a sua branch de feature, mantendo as alterações da feature intactas?

### Resposta do aluno

Para alternar rapidamente para a branch main, corrigir o bug e depois retornar à branch de feature sem perder o trabalho em andamento, o fluxo padrão utiliza o git stash (caso haja arquivos modificados ainda não commitados) e a troca de branches:

    Guardar alterações não commitadas (se houver):
    Bash

    git stash

    (Se tudo já estiver commitado na branch de feature, esse passo pode ser ignorado).

    Alternar para a branch principal (main):
    Bash

    git checkout main
    # ou: git switch main

    Atualizar a main, criar uma branch de hotfix (boa prática) ou aplicar a correção diretamente:
    Bash

    git pull origin main
    # Faz a correção do bug, adiciona e commita:
    git add .
    git commit -m "fix: corrige bug crítico"
    git push origin main

    Retornar para a branch de feature:
    Bash

    git checkout nome-da-branch-feature
    # ou: git switch nome-da-branch-feature

    Recuperar o trabalho pendente guardado no stash:
    Bash

    git stash pop

(Opcionalmente, após voltar à feature, vale rodar um git merge main ou git rebase main para trazer o fix recém-aplicado para a sua feature).

Vamos para a última pergunta. Agora, pense no contexto de um Github Action. Você criou um workflow para rodar testes automaticamente sempre que alguém envia um `push` para a branch `main`. Se você quiser que esse workflow **não** rode quando você fizer um `push` em uma branch chamada `develop` (mas que rode em todas as outras branches que não sejam `main` ou `develop`), como você configuraria o gatilho (`on.push.branches`) no seu arquivo YAML para atingir esse objetivo?

### Resposta do aluno

Para fazer com que o workflow rode em todas as branches, exceto na develop (ou qualquer outra especificada como main), você pode configurar o gatilho de duas formas principais no GitHub Actions:
1. Usando a chave branches-ignore (Mais comum e direta)
YAML

on:
  push:
    branches-ignore:
      - 'develop'
      # se quiser ignorar a main também:
      # - 'main'

2. Usando padrão de negação (!) dentro de branches
YAML

on:
  push:
    branches:
      - '*'          # Corresponde a qualquer branch
      - '!develop'   # Exclui a branch develop
      # - '!main'    # Exclui a main, se aplicável

(Observação: No GitHub Actions, não é permitido misturar branches e branches-ignore no mesmo gatilho; deve-se optar por uma das duas abordagens).
